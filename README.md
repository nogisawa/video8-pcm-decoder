# Video8 PCM decoder (Python)

CXADC FLACからNTSC Video8 PCMを復調します。既存のNumPy/SciPy復調器を移植し、
CRC検査、デインタリーブ、16-bit stereo WAV化を独立したコマンドにしました。

## 準備

Python 3.10以降と `numpy`, `scipy`, `soundfile` が必要です。`soundfile` は環境に
よってOSの `libsndfile` を使います。

```sh
python3 -m pip install -r requirements.txt
```

## 使い方

```sh
python3 v8tune.py input.flac
python3 v8demod.py input.flac -o pcm.v8t --sample-rate 28636360
python3 v8crc.py pcm.v8t --show-bad
python3 v8wav.py pcm.v8t output.wav
```

`v8tune.py` は実クロックと方式が不明な時の探索用です。FLACメタデータのレートが
1 MHz未満なら、`v8demod.py` はCXADCの慣例に合わせ1000倍します。
`--start` と `--duration` は実時間の秒です。`--phases` を増やすと探索は遅くなります。
通常のFLACファイルでは、指定した解析範囲の処理済み割合をstderrへ表示します。

既定の `--scan-mode track` はプリアンブルとf1〜f4のパイロットを検知し、
その少し手前から約1トラック分をメモリへ読みます。先頭側のCRC正常ブロックで
トラックの始点を決めます。各ブロックではまず狭い位相範囲を一括判定し、
CRC正常ブロックから周辺の位相を予測します。予測が外れた位置だけ探索範囲を
広げ、なおCRCが通らない位置は前後約1ブロックを含む窓でビット位置と
位相を総当たりして回復を試みます。
従来の全域探索は `--scan-mode exhaustive` で実行できます。
このモードでも各フィールドの元FLAC上の位置と欠落情報を `.v8t` に保存します。
実キャプチャ5.177秒では310トラックを13.93秒で処理し、CRC不良は7/40,920
ブロックでした（この環境での実測）。

WAVは 31,469 Hz、signed 16-bit、stereoです。既定ではNTSCのP/Qパリティで
CRC不良ブロックを復元し、復元できないサンプルとその前後1サンプルを補間します。
15 kHzの2次ローパスも適用します。`--crc-guard 0`、`--lowpass 0`、
`--use-bad-crc` で各処理を変更できます。

## 映像との同期

`pcm.v8t` は元FLACのサンプル位置を各フィールドに記録します。フィールドが検出
できない時間には欠落レコードを挿入します。CRC不良ブロックも破棄せず記録します。
`v8wav.py` は既定でFLACの時刻0をWAVの時刻0に対応させ、開始前や欠落部分には
無音を入れます。短い範囲だけ取り出す場合は `--origin first` で最初に検出した
フィールドをWAVの先頭にできます。映像との同期には既定の `capture` を使い、映像と
FLACの録画開始時刻差がある場合はその差を別途適用してください。

バイナリ形式はlittle-endianです。24バイトのヘッダ
`<8sIdI`（magic=`V8PCMT01`, version=1, ADC sample rate, system=0=NTSC）の後に、
各フィールドを `uint64 field_number, uint64 rf_sample, uint32 flags` と
132×13バイトの物理ブロックで格納します。`flags & 1` が0なら欠落フィールドです。
物理ブロックはRust版と同じ `address,Q,W0..W3,P,W4..W7,CRC-low,CRC-high` です。

現在PAL音声のデインタリーブとP/Q訂正は未実装です。NTSCのP/Q訂正は
`v8wav.py` のWAV化時に適用します。欠落フィールドの番号は
検出フィールド間のRF時刻差から推定するため、録画開始前の欠落を番号だけで特定
することはできません。各レコードの `rf_sample` が同期の基準です。

## 大きなFLACの逐次処理

既定の `v8demod.py --scan-mode track` は、FLACを開いた後、
約0.1秒分ずつマーカーを調べ、見つかったトラックから順に復調して
`.v8t` に書き込みます。ファイル全体のマーカー検出が終わるまで
復調開始を待ちません。進捗はstderrに入力時刻と処理済みトラック数で表示します。
`v8markers.py` 単独実行もJSON行を順次書き出します。

FLAC全体をNumPy配列へ読み込まないため、既定モードの作業メモリは
入力の長さではなく、約0.1秒の検出チャンクと1トラックの復調窓で決まります。
添付の5.177秒キャプチャでは、従来版と出力がバイト一致し、
最大常駐メモリは約190MBでした。実際の使用量はライブラリと入力条件で変わります。
`exhaustive`、`locked`、`markers` の各旧モードは候補を全域で保持するため、
巨大なFLACには既定の `track` モードを使ってください。

## NTSC P/Q誤り訂正

`v8wav.py` は既定で、1フィールド132ブロック内を循環するP/Q偶数パリティを使います。
CRC不良ブロックの10ワードを消失として扱い、他の既知ワードから一意に求まる
ワードだけを復元します。複数ブロックが壊れていて復元できないサンプルは
従来どおり補間します。元の `.v8t` と記録CRCは変更しません。

CRCを通った誤判定についても、すべての不一致パリティ検査が一つのブロックを
指し、復元後に全P/Q検査が一致する場合に限り訂正します。
比較用に訂正を止めるときは `--no-pq` を指定します。
`--use-bad-crc` は従来どおり生のハード判定を使い、P/Q訂正も行いません。

```sh
python3 v8wav.py capture.v8t corrected.wav
python3 v8wav.py capture.v8t uncorrected.wav --no-pq
```

添付の5.177秒キャプチャではCRC不良7ブロックを全て復元し、
CRCを通っていた誤判定1ブロックもP/Qの整合性から訂正しました。
stderrに訂正数と未復元数を表示します。
`v8demod.py`、`v8crc.py`、`v8wav.py` は完了時に元の入力ブロックの
CRCエラーレートを％で表示します。分母は存在するフィールドのブロック数で、
欠落フィールドは別に数えます。P/Q検査の間隔は
[JIS C 5583-1992の図30](https://kikakurui.com/c5/C5583-1992-01.html)
に従います。

## CPU/GPUバックエンドの境界

現在はCPUのみです。`demod_backend.py` が解析窓のバッチ、RF帯域フィルタ、
CRC不良ブロックの再判定のインターフェースを定義し、`cpu_backend.py` が
NumPy/SciPyで実装します。`video8pcm.py` と `v8demod.py` はバックエンドを
引数として受け取り、FLAC読み込み、フィールド整列、タイムスタンプと
中間ファイルの書き込みを担当します。

GPU対応時は同じ `DemodBackend` を実装して選択処理を追加します。
`scan_windows` は最大16窓をまとめて渡すため、GPUへの転送をまとめられます。
バイナリ形式とWAV変換はバックエンドに依存しません。CPU/GPUの結果は
実キャプチャでCRC検出数、ブロック内容、フィールド時刻を比較してください。

## CPU高速化

位相ごとのCRC探索では、ビットを8通りのバイト境界で一度ずつパックして
再利用します。CRCの各バイトの寄与を事前計算し、均一間隔のADCサンプルに
対する線形補間も専用の配列演算に変更しました。0.5秒の実キャプチャでは、元Python版の7.04秒に対して
3.66秒で、出力した全51,480バイトが一致しました（この環境での実測）。
短い入力ではNumPy/SciPyの読み込み時間が占める割合が大きくなります。

## CRC不一致時の再探索

既知のCRC正常ブロックで埋まらなかった位置は予測位置付近の19位相を試します。
CRC正常ブロックが見つかった時点で打ち切ります。再探索を無効にした比較では
0.5秒の実キャプチャのCRC不良が10件から44件へ増え、速度改善はほぼありませんでした。

## プリアンブルとトラッキングパイロットの検出

PCMを復号せずに信号位置だけを調べる場合:

```sh
python3 v8markers.py input.flac --sample-rate 28636360 -o markers.jsonl
```

プリアンブルは規格の「クロックランイン」です。全ビットが1なので、
約5.79 MHz（NTSC）の短いトーンとして検出します。約2.7 ms後の
アフタレコードマージンにも同じトーンがあり、対になった場合だけ
トラックとして出力します。各トラックの中間2 msだけを調べて
f1〜f4のトラッキングパイロットを分類します。NTSCの公称周波数は
f1=102544、f2=118951、f3=165210、f4=148689 Hzです。
PALも `--system pal` で周波数を切り替えられます。

出力の `preamble_peak_seconds` はFFT窓の中心に基づくトーンピーク時刻で、
プリアンブルの厳密な開始境界ではありません。`pilot_confidence` は最大候補と
次点の強度比です。stderrにプリアンブル走査、パイロット判定、合計の秒数を
表示します。弱い素材では `--threshold` を調整できます。

周波数とクロックランインの仕様は
[JIS C 5583-1992](https://kikakurui.com/c5/C5583-1992-01.html) の
22.3節と25.1節に基づきます。

### 実測（PCM復号なし）

添付キャプチャ5.177秒で310トラックを検出し、f1〜f4の並びは全区間で
連続しました。FFT窓8192サンプル、ホップ6144サンプルで、同じ実行を
連続3回測った内部処理時間は3.275秒、3.261秒、3.277秒でした。
内訳はプリアンブル走査が約2.60秒、パイロット分類が約0.67秒です。
Python/SciPyの起動・読み込みを含むプロセス時間は環境負荷によって変わります。
4096サンプルのホップでも310トラックを検出しましたが、8192にすると
259トラックに減ったため、6144を採用しています。
